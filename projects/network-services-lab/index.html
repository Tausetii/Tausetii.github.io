PROJECT WRITE-UP / NETWORK SERVICES

Network Services Lab

Based on the supplied lab documentation · Detailed build notes · Download original PDF

This lab was a full network-services build rather than a single-server exercise. I configured a routed LAN, created a two-controller Active Directory environment, joined Windows and Linux machines to the domain, connected two WordPress deployments to MySQL, and added SMB, SFTP, Rocket.Chat, NextCloud, IIS, and an NGINX reverse proxy. The final stage focused on restricting communication to the ports and hosts each service actually needed.

Assignment

The assignment required a working multi-machine environment where infrastructure services supported application services. The important constraint was the interaction between systems: DNS had to work before domain joining, the WordPress sites had to reach a separate MySQL server, IIS had to be placed behind NGINX, and sensitive shares had to be limited to the Windows 10 client.

The original assignment brief is available as Evan’s Lab (Retyped) ↗.

Build sequence
Router and IPs → DNS and domain controllers → domain joining → MySQL → web applications → file services → firewall restrictions and testing.

Network configuration

Windows machines

  1. Open Control Panel → View Network Status and Tasks → Change Adapter Settings.
  2. Right-click Ethernet → Properties → Internet Protocol Version 4 (TCP/IPv4).
  3. Select Use the following IP address and enter the machine’s IP from the environment table.
  4. Use 192.168.1.1 as the default gateway.
  5. During initial setup, use Google DNS if needed for Internet access.
  6. After AD is working, return to the same screen and set DNS to 192.168.1.12 and 192.168.1.20.
IP address:       192.168.1.x/24
Default gateway:  192.168.1.1
DNS after AD:     192.168.1.12, 192.168.1.20

Linux machines

  1. On FTP1, run sudo chmod 600 /etc/netplan/50-cloud-init.yaml.
  2. Edit the file with the machine’s address, router gateway, and DNS values, then apply Netplan.
  3. On SQL1 and WEB3, open Settings → Wired Network → IPv4, disable automatic addressing, enter the static IP, gateway, and DNS, and apply the connection.
  4. On WEB2, edit /etc/NetworkManager/system-connections/ens18.nmconnection.
  5. Run sudo nmcli connection reload, then sudo nmcli connection up ens18.
sudo chmod 600 /etc/NetworkManager/system-connections/ens18.nmconnection
sudo nmcli connection reload
sudo nmcli connection up ens18

For the Windows Server 2016 DNS issue, I used the domain controller to add a DNS forwarder and clear the cache:

Add-DnsServerForwarder 8.8.8.8
Clear-DnsServerCache -Force

Active Directory and domain joining

DC1: primary domain controller

  1. Open Server Manager → Manage → Add Roles and Features.
  2. Choose a role-based installation, select Active Directory Domain Services, and install it.
  3. Rename the computer before promotion.
  4. Use the Server Manager notification flag and select Promote this server to a domain controller.
  5. Choose Add a new forest, enter the lab FQDN, set the functional level, keep DNS selected, complete the prerequisite check, and restart.

DC2: secondary domain controller

  1. Install AD DS on DC2 using the same role-based workflow.
  2. Set preferred DNS to 192.168.1.12 and alternate DNS to localhost.
  3. Choose Add a domain controller to an existing domain.
  4. Enter domain administrator credentials, keep DNS and Global Catalog selected, choose DC1 as the replication source, and install.
  5. After the restart, confirm that DNS and replication work before joining other machines.

Linux realm joining

  1. Change the Linux DNS servers to 192.168.1.12 and 192.168.1.20.
  2. Run realm discover {FQDN} to confirm the domain is visible.
  3. Run realm join {FQDN} and enter the domain administrator credentials.
  4. Add session optional pam_mkhomedir.so skel=/etc/skel umask=077 to /etc/pam.d/common-session.
  5. Sign in as Administrator@{FQDN} to verify the machine joined successfully.
realm discover {FQDN}
realm join {FQDN}

# /etc/pam.d/common-session
session optional pam_mkhomedir.so skel=/etc/skel umask=077

Validation

The practical check was whether each machine could resolve the domain, authenticate with domain credentials, and communicate with services by hostname or IP. If DNS still pointed at a public resolver, domain discovery and authentication failed even when the IP configuration looked correct.

Web services

WEB1: XAMPP and WordPress

  1. Install XAMPP on WEB1 and keep the required components, MySQL, and phpMyAdmin selected.
  2. Download WordPress and extract it into C:\xampp\htdocs\.
  3. Start Apache from the XAMPP Control Panel.
  4. On SQL1, create a database and a user with host % because WEB1 connects remotely.
  5. Open http://localhost:80/wordpress/wp-admin on WEB1.
  6. Enter the SQL1 database name, username, password, and 192.168.1.17 as the database host.
  7. Complete the site title and WordPress administrator fields, run the installation, and log in.
CREATE DATABASE {database-name};
CREATE USER '{username}'@'%' IDENTIFIED BY '{password}';
GRANT ALL PRIVILEGES ON {database-name}.* TO '{username}'@'%';

I started Apache from the XAMPP Control Panel, then opened http://localhost:80/wordpress/wp-admin on WEB1. In the WordPress database screen, I entered the database name created on SQL1, the SQL1 user and password, and 192.168.1.17 as the database host. After WordPress connected, I entered the site title, WordPress administrator username, administrator password, and email, clicked Run the Installation, and logged in to verify the site.

WEB2: Apache and WordPress

  1. Update CentOS and install Apache: sudo yum update -y, then sudo yum install httpd -y.
  2. Start and enable Apache with sudo systemctl start httpd and sudo systemctl enable httpd.
  3. Install PHP and the MySQL module: sudo yum install php php-mysqlnd -y.
  4. Download and extract WordPress, then copy it into /var/www/html/.
  5. Create /var/www/html/wp-content/uploads.
  6. Set ownership and permissions so Apache can serve WordPress and write uploads.
sudo yum update -y
sudo yum install httpd -y
sudo systemctl start httpd
sudo systemctl enable httpd
sudo yum install php -y
sudo yum install php-mysqlnd -y
sudo systemctl restart httpd

Configure WordPress to use SQL1

  1. Copy the sample config: sudo cp /var/www/html/wordpress/wp-config-sample.php /var/www/html/wordpress/wp-config.php.
  2. Open wp-config.php and set DB_NAME to the SQL1 database.
  3. Set DB_USER and DB_PASSWORD to the MySQL account created for WEB2.
  4. Set DB_HOST to 192.168.1.17. Do not use localhost because MySQL is on SQL1.
  5. Set Apache ownership and confirm that the uploads directory is writable.

Finish and test the site

  1. From WKS1, open http://{CentOS-External-IP}/wordpress. This is the WAN-facing or 1:1-NAT address, not WEB2’s private LAN address.
  2. Enter the database name, SQL1 IP, database username, and database password when WordPress asks for them.
  3. Enter the site title, WordPress administrator username, administrator password, and email.
  4. Click Run the Installation, then log in to confirm the site works from another machine.

WEB3: NGINX reverse proxy for IIS

  1. On DC2, open Server Manager → Add Roles and Features.
  2. Select Web Server (IIS), accept the default feature selections, and install it.
  3. From WKS1, open http://192.168.1.20:80 and confirm the default IIS page works.
  4. On WEB3, install NGINX and back up the default site.
  5. Edit /etc/nginx/sites-enabled/default and set proxy_pass to http://192.168.1.20:80.
  6. Run sudo nginx -t, restart NGINX, and open the WEB3 address from WKS1.
sudo apt update && sudo apt upgrade
sudo apt install nginx -y
sudo systemctl start nginx
sudo systemctl enable nginx
sudo cp /etc/nginx/sites-enabled/default /etc/nginx/sites-available/default-backup
sudo nginx -t
sudo systemctl restart nginx
server {
    listen 80;
    server_name localhost;
    location / {
        proxy_pass http://192.168.1.20:80;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

Data and collaboration services

SQL1: MySQL

  1. Update Ubuntu and install MySQL.
  2. Check the service with sudo systemctl status mysql; start it if necessary.
  3. Run sudo mysql_secure_installation and choose the hardening options.
  4. Open /etc/mysql/mysql.conf.d/mysqld.cnf and change bind-address to 0.0.0.0.
  5. Restart MySQL.
  6. Create one database and account for each WordPress site using CREATE DATABASE, CREATE USER, and GRANT ALL PRIVILEGES.
  7. Use firewall rules to permit TCP 3306 only from WEB1 and WEB2.
sudo apt-get update
sudo apt install mysql-server -y
sudo systemctl status mysql
sudo mysql_secure_installation
sudo systemctl restart mysql
sudo nano /etc/mysql/mysql.conf.d/mysqld.cnf

Rocket.Chat on SQL1

  1. Install Rocket.Chat with sudo snap install rocketchat.server.
  2. Open http://localhost:3000 on SQL1.
  3. Enter the administrator account, organization information, and admin email.
  4. Check systemctl status snap.rocketchat-server.rocketchat-server.service.
  5. Allow the application port only from the hosts that need access.
sudo snap install rocketchat.server
systemctl status snap.rocketchat-server.rocketchat-server.service

NextCloud on FTP1

  1. Install NextCloud with sudo snap install nextcloud.
  2. On SQL1, create the NextCloud database, user, and privileges.
  3. Install the required PHP modules on FTP1.
  4. Configure Apache to listen on port 8080 and enable the NextCloud virtual host.
  5. From WKS1, open http://192.168.1.18:8080.
  6. Enter SQL1’s address, database name, database username, and database password in the NextCloud installer.
sudo snap install nextcloud
sudo apt install -y php-gd php-mysql php-curl php-mbstring php-intl php-xml php-zip php-bcmath php-gmp php-imagick php-apcu

File services

SMB1: proprietary data

  1. On a domain controller, open Active Directory Users and Computers → Domain → Users.
  2. Create the domain account and record its username and password.
  3. On SMB1, create the shared file or folder.
  4. Open Properties → Sharing → Share → Find People, enter the domain account, check the name, and complete the wizard.
  5. On WKS1, open This PC → Map network drive.
  6. Enter \\192.168.1.20\{shared-file-name}, select Connect using different credentials, and authenticate as the new domain user.
\\192.168.1.20\{shared-file-name}

FTP1: restricted SFTP

  1. Install OpenSSH with sudo apt install openssh-server -y.
  2. Edit /etc/ssh/sshd_config and add a Match Group block with ChrootDirectory %h, X11Forwarding no, AllowTcpForwarding no, and ForceCommand internal-sftp.
  3. Restart SSH and confirm its status.
  4. Create the SFTP group and user with a non-login shell.
  5. Make /srv/{username} owned by root, then create a nested data directory owned by the SFTP user.
  6. From WKS1, run sftp {username}@192.168.1.18 and confirm the user is confined to the chroot.
sudo apt update && sudo apt upgrade -y
sudo apt install openssh-server -y
sudo groupadd {group-name}
sudo useradd -m -G {group-name} -s /usr/sbin/nologin {username}
sudo passwd {username}
sudo mkdir -p /srv/{username}/{directory}
sudo chown root /srv/{username}
sudo chmod g+rx /srv/{username}
sudo chown {username}:{username} /srv/{username}/{directory}

The connection test was performed from WKS1:

sftp {username}@192.168.1.18

Security controls

Each security requirement became a specific firewall or hardening action. The sections below show the source, destination, port, and default policy for each control.

SMB and proprietary data

SMB1 allows TCP 445 inbound from the Windows 10 client only. The Windows firewall profiles remain enabled with inbound traffic blocked by default.

New-NetFirewallRule -DisplayName "{Any Name}" -Protocol TCP -LocalPort 445 -RemoteAddress 192.168.1.16 -Direction Inbound -Action Allow
Set-NetFirewallProfile -Profile Domain,Private,Public -Enabled True -DefaultInboundAction Block

SFTP and HR data

FTP1 allows SSH only from WKS1. The SFTP account is contained by its group membership, password, non-login shell, and chroot directory.

sudo iptables -A INPUT -i lo -j ACCEPT
sudo iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
sudo iptables -A INPUT -p tcp --dport 22 -s 192.168.1.16 -j ACCEPT
sudo iptables -P INPUT DROP

IIS behind NGINX

DC2 allows HTTP only from WEB3. This makes the reverse proxy the intended path to IIS instead of leaving the web server reachable from every interface.

New-NetFirewallRule -DisplayName "{Any Name}" -Profile Domain,Public,Private -Protocol TCP -LocalPort 80 -RemoteAddress 192.168.1.15 -Action Allow

SMBv1 and EternalBlue

The assignment’s “different beast” clue refers to EternalBlue, which exploited SMBv1. The mitigation is to disable SMBv1 and use SMBv2 or SMBv3.

Disable-WindowsOptionalFeature -Online -FeatureName SMB1Protocol

PCI-DSS requirement 1

PCI-DSS requirement 1 is about installing and maintaining a firewall configuration. In this lab, I interpreted that as a default-deny design: enable the host firewall, block unsolicited traffic, then add narrow allow rules for the exact source IP and destination port required by each service.

How to read the rules

  • -A INPUT adds a rule for traffic arriving at the machine.
  • -A OUTPUT adds a rule for traffic leaving the machine.
  • -s is the allowed source IP; -d is the destination IP.
  • --dport identifies the service port, such as 22 for SSH or 3306 for MySQL.
  • ESTABLISHED,RELATED allows replies for connections that were already permitted.
  • -P INPUT DROP and -P OUTPUT DROP make the default action deny.

Linux firewall pattern

For Linux hosts, I first flushed old rules so the test started from a known state. I then allowed loopback traffic and replies to existing connections, added the service-specific allow rules, and set the default policies to DROP. The order matters: the established-connection rules must appear before the final DROP policies.

sudo iptables -F
sudo iptables -A INPUT -i lo -j ACCEPT
sudo iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
sudo iptables -A OUTPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT

SQL1: MySQL only from the web servers

SQL1 receives MySQL connections only from WEB1 and WEB2. The -p tcp and --dport 3306 conditions prevent unrelated protocols and ports from reaching the database.

sudo iptables -A INPUT -p tcp -s 192.168.1.19 --dport 3306 -j ACCEPT
sudo iptables -A INPUT -p tcp -s 192.168.1.13 --dport 3306 -j ACCEPT
sudo iptables -P OUTPUT DROP
sudo iptables -P INPUT DROP

WEB1 and WEB2: web traffic in, database traffic out

The web servers accept HTTP from WKS1 and can initiate MySQL connections to SQL1. They do not need to accept arbitrary inbound connections or initiate arbitrary outbound connections.

# WEB1 / Windows firewall equivalent
New-NetFirewallRule -DisplayName "Allow HTTP from WKS1" -Protocol TCP -LocalPort 80 -RemoteAddress 192.168.1.16 -Direction Inbound -Action Allow

# WEB2 / iptables
sudo iptables -A INPUT -p tcp -s 192.168.1.16 --dport 80 -j ACCEPT
sudo iptables -A OUTPUT -p tcp -d 192.168.1.17 --dport 3306 -j ACCEPT
sudo iptables -P OUTPUT DROP
sudo iptables -P INPUT DROP

WEB3: restrict the reverse proxy path

WEB3 accepts HTTP from WKS1 and sends HTTP only to DC2. This prevents a client from using WEB3 as a general proxy to other hosts.

sudo iptables -A INPUT -p tcp -s 192.168.1.16 --dport 80 -j ACCEPT
sudo iptables -A OUTPUT -p tcp -d 192.168.1.20 --dport 80 -j ACCEPT
sudo iptables -P OUTPUT DROP
sudo iptables -P INPUT DROP

FTP1: SFTP only from WKS1

FTP1 allows TCP 22 from WKS1 and denies other inbound traffic. The loopback and established-connection rules keep local services and replies working.

sudo iptables -A INPUT -i lo -j ACCEPT
sudo iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
sudo iptables -A INPUT -p tcp -s 192.168.1.16 --dport 22 -j ACCEPT
sudo iptables -P OUTPUT DROP
sudo iptables -P INPUT DROP

SMB1: Windows firewall rules

SMB1 permits TCP 445 only from WKS1. The Windows firewall profiles are enabled and their default inbound action is Block. A second outbound rule can restrict SMB1’s domain-controller communication if the lab requires outbound default deny.

New-NetFirewallRule -DisplayName "Allow SMB from WKS1" -Protocol TCP -LocalPort 445 -RemoteAddress 192.168.1.16 -Direction Inbound -Action Allow
Set-NetFirewallProfile -Profile Domain,Private,Public -Enabled True -DefaultInboundAction Block

DC2: IIS is reachable only from WEB3

DC2 allows TCP 80 from WEB3. The rule is deliberately narrower than “allow HTTP from any host,” because the purpose of the reverse proxy is to keep direct IIS access restricted.

New-NetFirewallRule -DisplayName "Allow IIS from WEB3" -Profile Domain,Public,Private -Protocol TCP -LocalPort 80 -RemoteAddress 192.168.1.15 -Direction Inbound -Action Allow

Disable SMBv1

The assignment’s “different beast” clue refers to EternalBlue, which exploited SMBv1. Disabling the feature removes the legacy protocol rather than relying only on a firewall rule.

Disable-WindowsOptionalFeature -Online -FeatureName SMB1Protocol

Global Windows default policy

For the Windows machines, the firewall profiles were kept enabled and unsolicited inbound traffic was blocked. The service rules above are exceptions to that default.

Set-NetFirewallProfile -Profile Domain,Private,Public -Enabled True -DefaultInboundAction Block

Validation

Test sequence

  1. Check IP addressing and DNS.
  2. Test domain discovery and authentication.
  3. Test the WordPress database connection from WEB1 and WEB2.
  4. Test Apache, XAMPP, and NGINX-to-IIS HTTP access from WKS1.
  5. Map the SMB share and test SFTP login from WKS1.
  6. Test Rocket.Chat on port 3000 and NextCloud on port 8080.
  7. Apply firewall rules and repeat each test from both allowed and disallowed sources.

Required paths should work; unrelated paths should fail:

  • Domain machines resolve the domain through DC1 and DC2.
  • WEB1 and WEB2 can reach MySQL on SQL1, but SQL1 does not accept arbitrary inbound sources.
  • WKS1 can reach the WordPress sites, NGINX, SMB, and SFTP paths required by the assignment.
  • The IIS site is reachable through WEB3 while direct access from unauthorized interfaces is blocked.
  • The SMB share and SFTP directory reject users or hosts outside the intended access path.
  • NGINX syntax validates with nginx -t before the service is restarted.
